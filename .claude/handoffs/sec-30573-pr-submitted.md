### CloudTrail window fix
- `ExtractSessionTimestamp` parses Unix timestamps (seconds or nanoseconds) from assumed-role session names; recognizes `dd-cloudiam-TIMESTAMP`, bare 19-digit nanosecond tokens and timestamps embedded mid-string
- `QueryCloudTrailOrigin` uses ±30min window when timestamp found; falls back to 36h otherwise
- Constant renamed from `cloudTrailNarrowWindow` to `cloudTrailIngestionBuffer`
- Empirically validated via Trino against prod org 2: 50 `vault-aws-secrets-backend` AssumeRole events, ingest_lag_ms=0 across all samples (CloudTrail event_time == session_timestamp by design)
- Targeted Trino query mirroring the fixed code returned the expected event, confirming the logic end-to-end

### Key findings from investigation
- `dd-cloudiam-TIMESTAMP` session names are generated by HashiCorp Vault's AWS secrets engine; Vault sets roleSessionName to the Unix second of credential issuance
- CloudTrail data for AWS account 727006795293 (Datadog staging) lives in PROD org 2, not staging org 2; staging ERS can't find it because the CloudTrail data isn't there
- `EntityEnricherService` in logs-backend uses signal timestamp as the query window upper bound (36h before signalTs); ERS currently uses `now` which is wrong for old credentials. Signal timestamp approach is a follow-up
- `entity_resolution.run` and child spans exist but aren't retained in APM due to missing retention filter; add one at https://ddstaging.datadoghq.com/apm/traces/retention-filters for `service:siem-entity-resolution-api @operation_name:(entity_resolution.run OR entity_resolution.fetch OR entity_resolution.pipeline OR entity_resolution.cloudtrail_query)`
