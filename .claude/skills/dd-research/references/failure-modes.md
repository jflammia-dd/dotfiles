# Failure Modes to Avoid

Read this before starting Phase 1. These entries catalog patterns from past sessions that produced wrong claims — specific enough that future sessions recognize them.

When a new failure mode is found during a research restart (Phase 3), add it here using the Edit tool. Use this format:
> - **[Pattern name].** What the draft claimed, what the code showed, why the research phase produced the wrong answer. What to do instead.

---

- **Stating things you can't verify from code.** If you haven't read the file, say so.
- **Accepting the user's repo suggestion without checking.** Always verify.
- **Using Confluence/docs as proof.** They're context. Code is proof.
- **Assuming when ambiguous.** Stop. Ask. Wait for an answer.
- **Summarizing READMEs as ground truth.** READMEs drift. Read the code.
- **Confusing what's planned with what's deployed.** Aspirational docs are not implementations. Feature flags, dead code, and half-implemented features are common. Check for these explicitly.
- **Inferring active deployment from file existence.** A `.ddsql`, `.sql`, `.java`, or `.go` file being present in the repo does not mean it's registered, scheduled or called in production. Find the activation config. See "The Exists ≠ Active Trap" in SKILL.md.
- **Describing a secondary code path as the primary behavior.** When a system has multiple query paths, feature-flag branches, or v1/v2 routes, verify which one runs by default before describing it as "how it works."
- **Skipping the verification pass.** Writing the output and calling it done without independently reviewing each claim is the single biggest source of errors. The verification pass is not optional — it is the last step of every research session.
- **Using subagents as a substitute for direct reads.** Dispatching a subagent to read a file produces `agent-verified` evidence, not `verified` evidence. Subagents are for discovery — finding which files to read, mapping directory structures, searching across large repos. The actual reading of every file cited in the output must happen in the main session. If the source table has entries that don't say "direct read," the research is not done.
- **Running the verification loop without applying the justins-voice skill.** If the voice skill is loaded at the start of the session but the prose was written before the loop ran, the loop will not catch style violations unless it explicitly checks for them. Always scan for em dashes (replace with commas, semicolons or parentheses), Oxford commas (remove the comma before the final "and" or "or") and comma-before-coordinating-conjunction in independent clauses (remove the comma) as part of every pass. Use a targeted grep for ` — ` and `, and ` to find violations quickly.
- **Recording a source table entry range that doesn't cover all lines cited in the prose.** If the doc cites `EntityRiskOutput.java:64` for the track definition AND `EntityRiskOutput.java:162` for the raw score computation, the source table entry must span at least lines 64–162. An entry of `:64-143` that silently omits the cited line 162 is a table inconsistency that will be caught by a later pass. When adding source table entries, check every prose citation for that file and make sure the range covers all of them. If the citations span widely, mark the file as fully read.
- **Adding a file to the source table as "direct read" without recording the line range or total line count.** When you read lines 1–60 of a 247-line file and add it to the source table as "direct read," the entry silently misrepresents coverage. Always run `wc -l` on every file when it first enters the source table, record the range actually read (e.g., "lines 1–60 of 247"), and keep reading until the full file is covered or the remaining lines are verified irrelevant. In the OCSF extractor case, AzureExtractor (270 lines), GcpExtractor (247 lines), M365Extractor (168 lines) and GitHubTelemetryExtractor (125 lines) were all added as "direct read" from initial reads of only their first 60–80 lines, masking hundreds of lines of unread extraction logic.
- **Stopping a file read before reaching the relevant method.** Reading lines 1–160 of a 488-line file and concluding you've read it is a partial read, not a complete one. Always check the total line count (via `wc -l`) and read the remainder if there are claims traced to that file. The OCSF parallel emission path in EntityRiskHandler lived at lines 174–184 — well past where the first-pass read stopped — and produced three prose corrections. If the file is large, read it in blocks; never leave it with an unchecked tail.
- **Claiming a feature flag applies universally when it only applies to experimental providers.** When a flag gates a behavior, verify which components override the default and what that default is. In the OCSF extraction case, the flag applied only to Azure and M365 (both explicit `isExperimental()` overrides returning `true`), while Okta, GCP and GitHub used the default `false` and always extracted. "A feature flag controls which providers use this path" was true but misrepresented the scope — most providers were unconditional. The root cause was reading 2 of 5 concrete implementations and applying the finding universally. Fix: when an interface has a default method that concrete classes may override, list all concrete classes in the directory (via `find` or `ls`) and count them before writing any universal claim. If you've read 2 of 5, read the other 3. Only after reading every concrete class can you say "all implementations do X."
- **Stopping at local repo boundaries without searching GitHub.** When a string or concept doesn't appear in locally-cloned repos, the next step is always `gh search code "TERM" --owner DataDog`, not "unable to verify." The full pipeline for `genresources` → `redaplinfra` was discoverable in one search: `gh search code "redaplinfra" --owner DataDog` immediately returned `dd-go/resources/repository/storage/backends/temporalhusky/writer.go: trackName = "redaplinfra"`. Five minutes of search resolved a gap that was marked "unable to verify" for days. Any gap where the string or concept name is known can and must be searched on GitHub before being declared unresolvable. The rule: local repo search and GitHub search are the same step, not two different steps. If you haven't run `gh search code`, you haven't searched.
- **Declaring "unable to verify" for a config default that's in an accessible library.** When a service creates a client with `NewXClient(WithGRPC(), WithSource(...))`, the track, timeout, and other defaults are in `NewXClientConfig()` in the same library. Not reading the config constructor and instead marking the claim "unable to verify" is a research failure. In the siem-entity-crawler case, `NewAsyncIntakeClient` with no `WithEventPlatformTrack()` option uses `defaultTrack = "genresources"` from `async_intake_client_config.go:22`. The answer was two files away and took two reads. Never stop at the interface boundary when the implementation is in a local repo.
- **Trusting a code comment over the actual function call.** Code comments can be wrong or aspirationally describe a different version of the code. In `shared.go`, the comment on line 59 said "Extract resource type from custom.type" but the actual call was `GetNestedValueOrDefault(entity.Attributes, "", "type")` — a top-level field, not nested under `custom`. The comment pointed at `custom.type`; the code extracted `type` at the top level. Always read the function call arguments, not the comment. When they diverge, the call wins. Document what the code does, not what the comment claims it does.
- **Citing a specific line number without verifying it.** Writing `config.go:116` when the actual line is 80 is a citation error that will mislead anyone who tries to verify the claim. Before committing a line number to the document, run `grep -n "TERM" file` or `gh api ... | base64 -d | grep -n "TERM"` to get the exact line. Never use `~line` approximations in a document that claims direct-read verification.
- **Using an illustrative example that contradicts a documented data format.** If the document describes a composite key format `{provider}_{entity_type}_{entity_id}`, any example that uses that key — in a URL, a query, or a code snippet — must match that format. Writing `@key:alice@example.com` when the actual key is `OKTA_user_identity_alice@example.com` is an internal inconsistency that will confuse readers. When writing examples that depend on a format defined elsewhere in the document, check the format and make the example conform to it.
- **Not updating section Source: footers when new claims are added.** A Source: footer that lists two files but the section makes claims backed by five files is undersourced. Every time a claim is added to a section, check whether the file it depends on is in that section's Source: footer. If it's missing, add it. The master source table is not a substitute for per-section footers — both need to be accurate.
- **Not adding GitHub API reads to the source table during investigation.** When reading a file via `gh api ... | base64 -d` to close a verification gap, that file must be added to the source table as "direct read (GitHub API, ...)" before moving on. In the siem-entity-crawler pipeline research, `genresources_decoder.go`, `config.go`, and `temporalhusky/writer.go` were all read via GitHub API during investigation but were initially missing from the source table. The claim "decodes the `RedaplEvent` proto" was backed by `genresources_decoder.go` but had no table entry until a later pass caught it. Read a file → add it to the table immediately, not at the end of the session.
- **Describing one code path when parallel paths serve different entity types.** When a handler processes both legacy and OCSF entities, describe both. EntityRiskHandler ran two streams (legacy `CloudEntity` filtered by `SUPPORTED_ENTITY_TYPES`, OCSF entities filtered by `isEntityRiskEnabledForCloudProvider`) that were concatenated. The original description only covered the legacy stream.
- **Using a directory-level source table entry to back a specific file-level claim.** Listing `entity-risk-score-api/` as "direct read" in the source table does not verify claims about specific files within that directory. The endpoint path `/api/ui/security-entities/risk-scores` required reading `main.go:175` — which was not in the source table — to verify. Any claim about a specific function, endpoint path, constant, or struct must be backed by the specific file where that thing is defined, not the directory. For RAPID services, the route registration is always in `main.go`. Add it to the source table explicitly.
- **Treating a declared DDSQL variable as proof the query uses it.** A DDSQL file that starts with `set start_time = timestamp '14d ago'` does not necessarily filter its output by that window. The variable is available for use but may not be referenced in the SELECT statements. `cloud_siem_entities_metadata.ddsql` declares `start_time` and `end_time` at the top of the file, but its SELECT queries read from cloud inventory tables (aws_iam_user, gcp_iam_service_account, azure_ad_user, etc.) without any WHERE clause referencing those variables. The result is a point-in-time snapshot with no time window filter, not a 14-day rolling window. Always read the SELECT body — not just the `set` declarations — before claiming a view has a particular time scope.
- **Not cross-checking terminology in Key Concepts against all sections that use it.** The streaming rules document listed `NETFLOW` as the CWS track in Key Concepts and `SECRUNTIME` as the CWS track in Stage 1 — both legitimate names from `CspMapperProcessor.SUPPORTED_TRACK_TYPES`, never acknowledged as distinct. Three blind Claude passes missed this; both adversarial reviewers caught it immediately. Root cause: verification passes check each section against code in isolation, not against other sections. Fix: during verification, do one explicit cross-section terminology pass — grep for every class/track/method name in Key Concepts and verify it appears consistently (or is explicitly distinguished) in all sections that reference the same concept.

- **Not checking list items against each other for internal contradictions.** Stage 3 listed `GenericPane` as handling "new-value rules" and then listed `NewValuePane` in the same numbered list as the concrete type for new-value detection. Both statements were individually consistent with the code; the contradiction only appeared between items. Three blind passes missed it. Fix: after reading each list that enumerates types or components, re-read the list as a set and ask: do any two items claim the same behavior? If so, investigate which one is correct.

- **Not applying the direction test to Mermaid diagram arrows.** The diagram showed `C -->|context blobs| CB` (mapper → blob storage), implying the mapper writes blobs. The prose said "the Context Loader fetches." A direction mismatch — arrow points to destination, verb says reads from it — went unnoticed through three blind passes. Fix: for each arrow in a diagram, find the corresponding prose sentence and apply the direction test: if the prose says "fetches/reads/loads," the arrow must point FROM the data source TO the consumer; if it says "publishes/writes/pushes," it must point FROM the producer TO the destination. A mismatch means one of the two is wrong.

- **Not scanning code blocks when correcting prose.** When a factual correction is made to narrative prose (the 99% → 80% fix), code blocks, timelines and worked examples that reproduce the same claim don't inherit the correction. In this session, "99%" was fixed in two prose locations but the timeline code block still said "WatermarkInjector confirms: 99%." Fix: immediately after every factual correction, grep the document for the old value to find any remaining occurrences — especially in fenced code blocks, which tend to be edited as prose but contain repeated claims.

- **Treating re-reading sources as equivalent to running the verification loop.** When verifying an existing document, the re-read phase (Steps 1-3 of verify-existing.md) closes the "stale reads" gap — it does not substitute for the verification loop. The loop has its own exit criteria: 3 consecutive clean Claude blind passes, then `dual-agents-review:dual-review`. A session that finds and fixes a substantive error during re-reading, then stops and updates the certificate, has skipped the loop entirely. The correct sequence is: re-read → fix → run 3 clean blind passes → run dual-review → only then update the certificate. The intuition that "I already found and fixed the main error, so there can't be more" is exactly what the loop exists to falsify. Never update the verification certificate to "Verified" without completing the loop.

- **Stopping at the transport layer and concluding there is no storage layer behind it.** A verification pass found that the evp-workers EventStore API routes through `libstorage` → `libstreaming` (Kafka-based) and concluded that Husky was not involved. This was wrong. Kafka is the transport layer; Husky is the storage layer behind it. Finding "writes to Kafka" does not mean "no persistent storage beyond Kafka." When verifying a claim about a service's storage backend, follow the full chain: producer → topic → consumer → storage. Stopping at any intermediate hop produces a false answer. In this case, the correct chain was: evp-workers `EventStore.write()` → libstreaming (Kafka) → Husky (EVP storage engine, backed by S3).

- **Attributing a behavior to the event that precedes it rather than the event that triggers it.** The SIEM scheduled rules document described `__hqLastEvent` as "finalizing the pane" — running all timers and flushing signals. The code (`SiemQueriesReducerProcessor.java:199-201`) shows the opposite: `isLastLog()` returns `ConsumptionResults.nothing()`, dropping the event immediately. Pane finalization happens via the delete timer in `onTimerInternal` (lines 391+), which fires `max-log-lateness` real time after the last log was received. Root cause: the researcher correctly read the delete timer path (which does run all timers and flush signals) and then attributed that behavior to the `__hqLastEvent` marker rather than to the timer. Fix: always read the handler for the specific event being described (`processEventInternal`) before stating what that event does. If the event handler returns early or drops the event, say so. Do not infer behavior from what happens after the event.

- **Stopping before the final conditional branch in a multi-branch method.** The SIEM scheduled rules checkpoint logic (`ScheduledRulesQueryProcessor.rewriteTimeRangeWithToken`) has four cases: (1) no token, (2) token ≥ shifted `to`, (3) token within range, (4) token < shifted `from`. The original document described only cases 1-3. Case 4 — `max(checkpointToken, from − 1 week)` — was in the final `else` block of the same method. Root cause: verified claims covering three branches and stopped, assuming no further branches existed. Fix: when reading a conditional method, always count the branches first (how many `if`/`else if`/`else` blocks?), then read every one. An unchecked `else` block is an unchecked claim.

- **Importing a stream-processing concept rather than reading the actual trigger condition.** The SIEM scheduled rules document said "a delete timer fires when the watermark advances past the pane's last event time." No watermark is involved. `HistoricalPane.getExpiryDate()` computes `timeWhenLastLogWasReceived + maxLogLatenessMillis`, where `timeWhenLastLogWasReceived` is real wall-clock time set in `consumeLog`. Root cause: "watermark" is a standard Flink/Akka Streams concept for advancing event time, and the researcher applied it without reading the actual implementation. Fix: whenever a description uses a domain concept that implies a specific mechanism (watermark, epoch, fence), find and read the method that computes the trigger condition and describe what the code actually computes, not what the concept suggests.

- **Deriving field naming from an external standard instead of reading the implementation.** When Datadog wraps an external standard (OCSF, OpenTelemetry, JSON API, etc.), the field names used in Datadog's implementation may diverge from the standard's canonical paths. In the OCSF case, OCSF itself defines the actor email at `actor.user.email_addr`. Datadog's implementation wraps OCSF data under `custom.ocsf.*` and observable `name` entries carry the prefix (`ocsf.actor.user.email_addr`). The Key Concepts section was written from the OCSF spec rather than from the code, so it showed the wrong format. The extractor constants (`Fields.ACTOR_EMAIL = "ocsf.actor.user.email_addr"`) were visible and correct, but the conceptual description of observables was written from the standard. Fix: whenever describing a field name or data structure from a system that implements an external standard, verify the format from test data or source constants, not from the standard's documentation. Unit tests are especially reliable — a test that constructs a document will use exactly the format the production code expects. The OktaExtractorTest showed `"name", "ocsf.actor.user.email_addr"` explicitly at line 52; reading it before writing the Key Concepts section would have prevented the error.

- **Naming a specific state when the code checks membership in a set of states.** The `raw_signal_score` claim said "severity × -1 for archived ones," but the actual logic is `severity × -1` for any state NOT in `ACTIVE_STATES`, which is defined as `Set.of(SignalState.OPEN, SignalState.UNDER_REVIEW)` (`EntityRiskOutput.java:30-31`). This excluded FALSE_POSITIVE, MUTED and any other non-active states. When making claims about state-based logic, always read the constant definition to see the full set. "Only applies to state X" and "applies to any non-active state" are materially different claims. Never describe a set membership check by naming only one element of the complement.
